# 要件: YouTube Super Lite を Chrome 拡張として再構成する

対象読者: この再構成を設計・実装する人。ネイティブ実装（mpv + DComp オーバーレイ + InnerTube リゾルバ）を
前提知識として持っている必要はない。廃棄される部分は §5 に列挙してある。

この文書は**要件**であって設計でも実装計画でもない。「何を満たせば成功か」だけを書く。

---

## 0. 何を作るのか

**公式 YouTube の watch ページから無駄を剥ぎ、視聴に必要な部分だけを残す Chrome 拡張。**
再生は YouTube 自身の公式プレーヤーが行う。拡張は再生機構を持たない。

現行のネイティブアプリ（`youtube-super-lite.exe`）を置き換える。

## 1. なぜ方向を変えるのか（判断の根拠）

「Super Lite」の目的は当初から**公式 Web UI の富豪的リソース使用からの脱却**であり、
その敵として名指しされていたのは **watch ページ全体**（おすすめ無限スクロール / コメント / 大量 DOM /
トラッキングの常時描画）。ブラウザエンジンの排除は目的ではない。

拡張はこの敵を直接攻める手段になる。加えて、ネイティブ実装が抱えていた次の問題が消える:

| 問題 | 現状 | 拡張では |
|---|---|---|
| ライブが再生できない（2026-07-04 の SABR 化以降） | ネイティブ経路で**再生実績ゼロ**。真因未特定・門は間欠 | YouTube 自身が再生するので発生しない |
| bot ゲート / PoToken / nsig / InnerTube client 版数の追随 | 壊れると**再生不能**。頻度が高い | ページのログインをそのまま使うので不要 |
| 自作 UI が使いづらい | DComp オーバーレイ（コードベース最大級の塊）の成果物が不満 | YouTube の UI を土台にして削る・足すだけ |
| EQ がライブで効かない | mpv の `af` 実装なので WebView2 経路（＝SABR 詰みライブ）では無効 | Web Audio で `<video>` に挿すので**全経路で効く** |
| 常時 Chromium 常駐 | WebView2 ホストを起動時から常時生成している | 単一の Chrome プロセスツリーに収まる |

**Why（この根拠の出所）:** 上記はいずれもこのリポジトリの記録・実測に基づく。特にライブについては
issue #16 の P0 / P0.5 / 案2 PoC / 参照実装検証を通して「ネイティブ SABR で映像が出た実績は無い」ことが
確定しており、唯一映像が出たのは「ログイン済み Chromium + 公式 embed」だけである。

## 2. 目的と評価軸

**目的:** 長時間視聴を含めて、公式 watch ページより軽く YouTube を視聴できるようにする。

**評価軸はリソース消費**。優先順位は次のとおり:

1. **長時間視聴での定常メモリ増加**（最優先。実害として観測されている）
2. 無駄なネットワークダウンロード量
3. 定常 CPU / GPU 負荷
4. 起動直後のピークメモリ

**明示的に目的でないもの:**

- **広告の回避は意図しない。** 広告表示それ自体は許容し、**広告の配信・表示に必要なリクエストは遮断しない**。
  ただし **広告に付随するトラッキング（効果測定・インタラクション報告・ID 同期）は遮断する**。
  これは広告を消すためではなく、他のトラッキングと同じ基準 —— **リソース消費** —— で判定した結果である。
  判定基準は「広告が表示されるか」ではなく「**表示に必要か**」。必要なら残し、計測だけなら落とす。
- 「ブラウザを走らせずに視聴する」ことは目的ではない。
- カスタム UI を持つこと自体は目的ではない（手段であって目的ではない）。

## 3. スコープ

**対象:** `www.youtube.com` の watch ページ（通常動画 / アーカイブ / ライブ配信）と、
そこに埋まるライブチャット iframe（`www.youtube.com/live_chat`）。

**スコープ外:**

- ホーム / 登録チャンネル / 履歴 / 再生リストの各ページ（YouTube のページをそのまま使う。§4 参照）
- YouTube 以外のサイト
- macOS / Firefox 対応（Chrome で成立させてから判断する。ただし §7 のとおり移植可能性は上がる）
- 動画のダウンロード・保存

## 4. 現行機能の帰属

現行の全機能を「YouTube に委譲」「拡張で実装」「廃棄」に分類する。**この表に無い機能を新規に足さない。**

### 4.1 YouTube に委譲する（拡張は何もしない）

| 現行機能 | 委譲先 |
|---|---|
| 動画再生・シーク・キャッシュ・DASH | 公式プレーヤー |
| 画質・コーデック選択 | プレーヤーの設定 UI（＋ §5.6 の誘導） |
| 再生速度切替 | プレーヤーの設定 UI |
| 一覧（おすすめ / 登録新着 / 履歴 / 再生リスト） | YouTube の各ページ。**watch ページ内のサイドバーは削るが、独立したページとしての一覧は残す** |
| ログイン | ブラウザのログイン状態 |
| 高評価 | プレーヤー下のボタン |
| 視聴履歴の記録 | YouTube が自動で行う |
| ライブチャットの取得・表示 | 公式チャット（ただし §5.3 で軽量化する） |
| URL 入力 | ブラウザのアドレスバー |
| 再生・音量・シークのキーボード操作 | YouTube 既定のショートカット |

### 4.2 拡張で実装する

§5 の機能要件に展開する。要約すると **①無駄の削減 ②EQ ③チャット表示調整** の 3 つだけ。

### 4.3 廃棄する

| 現行機能 | 廃棄理由 |
|---|---|
| GPU 負荷連動の自動 HW/SW デコード切替 | **発火が観測されたことがなく、価値を届けた形跡が無い。** 拡張に等価物も無い（§8） |
| 画像キャッシュ（`image_cache.rs`） | 自前の一覧描画をやめるので不要 |
| dev-tools（検証用ローカル HTTP） | 拡張では DevTools が使える |
| URL 入力欄・IME 非対応の制約 | アドレスバーに置き換わる |
| コントローラ帯 / ナビゲーション帯 / 一覧オーバーレイ | 不満の対象そのもの。YouTube の UI に置き換える |

## 5. 機能要件

### R1. 無駄なネットワークダウンロードを遮断する

`declarativeNetRequest` の静的ルールで、ページの JS が走る前にリクエストを遮断する。

**「テレメトリ」を一括りにして遮断してはならない。** 見た目が計測系でも、機能・思想・既存機能の
いずれかに紐づくものが混ざっている。次の 3 層に分けて扱う。

#### (a) 遮断してよい（純粋な計測・再生に関与しない）

- `/youtubei/v1/log_event` — クライアントイベントログ
- `/api/stats/qoe` — 再生品質のレポート。ABR の判断はこれに依存しない（送信専用）
- `/ptracking`
- **広告トラッキング** — `/api/stats/ads`、`/pagead/interaction/*`、`/pagead/viewthroughconversion/*`、
  ID 同期系。**広告の表示には不要な計測ビーコン**なので (a) に入る（§2 の判定基準）
- 削除対象領域のサムネイル（`i.ytimg.com`）— 関連動画・コメントを消すなら不要になる
- 次動画のプリフェッチ / preconnect

#### (b) 遮断してはならない（機能・認証に紐づく）

| 対象 | 理由 |
|---|---|
| `/youtubei/v1/player/heartbeat` | **計測ではない。** ライブの配信状態のポーリングと「まだ見ていますか」の判定に使われる。止めるとライブ再生が壊れ得る |
| attestation / BotGuard 系（`/youtubei/v1/att/*` 等） | **この方向転換の前提そのもの。** YouTube の bot 判定を通ることに依存しているので、その通信を妨害してはならない |
| `/api/stats/playback`・`/api/stats/watchtime` | **視聴履歴の記録経路。視聴履歴は維持すると決定済み**（ユーザー決定 2026-07-27）。したがって遮断しない。軽量化と引き換えにしない |

#### (c) 遮断しない（思想上の制約）

**広告の配信・表示に必要なリクエストは対象に含めない。** 広告は表示されたままにする（§2）。

境界は「広告か否か」ではなく「**表示に必要か否か**」で引く。したがって広告トラッキング
（`atr` 等の効果測定ビーコン）は (a) に入り、遮断する。広告そのものの取得・再生・描画に
関わるものだけが (c) に残る。

**優先度の注記:** 広告ビーコンは 1 本あたりが小さく、削減量はコメント・関連動画・チャット画像に
比べて桁が小さいと見込まれる。R1 の中では**効果の期待値が低い項目**として扱い、§6 で実測して
効果が無ければ維持コストをかけない。

**受け入れ条件:** 遮断有効時に、再生・シーク・**ライブの継続再生**・チャット受信・ログイン状態・
視聴履歴の記録のいずれも壊れない。
**要検証:** (b) の各エンドポイントが実際に機能に紐づいているかは、遮断してから壊れることを
確認するのではなく、**1 本ずつ遮断して差分を取る**（§9-5）。

### R2. コメント・関連動画を「作らせない」

`document_start` / `world: "MAIN"` の content script で `fetch`（および `XMLHttpRequest`）を差し替え、
watch ページのデータ応答からコメントスレッドと関連動画の `continuationItems` を落として
ページに渡す。DOM を構築させないことで、削除ではなく**構築コストそのものを発生させない**。

**実測で確認済み（2026-07-27・アプリ内ブラウザで watch ページを実行）:**

| 確認事項 | 結果 |
|---|---|
| YouTube のネットワーク層が `fetch` / `XHR` を経由するか | **経由する。両方とも差し替えで捕捉できた**（R2 はデータ層で成立。DOM 層へのフォールバックは不要） |
| watch ページのデータ取得先 | **`/youtubei/v1/get_watch`（`fetch`）**。当初 `/youtubei/v1/next` と書いていたが誤り |
| メディアセグメント | `googlevideo.com/videoplayback` も **`fetch` 経由**（＝介入可能。本要件では触らない） |
| SPA 遷移後もパッチが生きるか | **生きる。** 自動再生で別動画へ遷移した後も捕捉が継続した（§R7 の前提を実証） |
| 経由の内訳 | `fetch`: `get_watch` / `api/stats/qoe` / `ptracking` / `videoplayback`　`XHR`: `api/stats/watchtime` / `api/stats/playback` / `api/stats/atr` / `api/timedtext` |

**未確認:** コメントスレッドの継続取得エンドポイント名。検証環境（未ログイン）ではコメントが
スケルトンのまま読み込まれず、該当リクエストが発生しなかった。実装時に実ブラウザで確定させる。

**受け入れ条件:**
- コメント欄・関連動画サイドバーが DOM 上に存在しない（`display:none` ではない）
- 動画の再生・タイトル・チャンネル情報・高評価は正常に機能する
- SPA 遷移後も効き続ける（§R7）

**要検証:** YouTube 自身のネットワーク層が `fetch` / `XHR` を経由しているか。経由していない場合は
DOM 層での除去（構築後の削除）にフォールバックする。この場合ピークコストは下がらない。

### R3. ライブチャットの長時間劣化を抑える

ライブチャット iframe（`www.youtube.com/live_chat`、同一オリジン）に `all_frames` で介入する。

要件:

- 保持メッセージ数に上限を設け、超過分を DOM から除去する（YouTube 自身の上限より厳しく）
- **視聴時間とともに種類が増える画像を読み込まない**（下記）
- **投稿者アバターは「モデレーターの投稿のみ表示」とする**（下記）

#### 落とす画像の基準（ユーザー決定 2026-08-02）

**基準は「装飾かどうか」ではなく「種類が増え続けるかどうか」。** この項目が抑えたいのは長時間視聴での
定常増加であって 1 枚あたりの重さではないため、判断は枚数の伸び方で決める。

落とす（発言者が変わるたびに別の URL が来る）:

- 投稿者アイコン（`authorPhoto`。ただし下記の例外あり）
- ギフト送信者のアイコン（`authorAvatar`）、ティッカーの投稿者アイコン（`sponsorPhoto`）

落とさない（配信あたりの種類が有限で、同じ URL を使い回す）:

- 絵文字・**メンバーシップ専用スタンプ**（`emoji`）、有料スタンプ（`sticker`）
- ギフト画像（`giftImage`）、❤ のチャンネル所有者アイコン（`creatorThumbnail`）
- メンバーバッジ（`customThumbnail`、決定 2026-08-01）

当初は「絵文字・スタンプ・スーパーチャット装飾を落とす」と定めていたが、これらは有限個であり
基準に合わないため、上記のとおり残す側へ変更した。

#### アバターの選択的除去

**URL による一括遮断（`yt3.ggpht.com` を DNR で落とす）は採用しない。** モデレーターのアバターも
巻き添えで消えるため。判定に必要な情報（`authorBadges`）はアバター URL と同じレスポンスに
入っているので、**ネットワーク層ではなくデータ層で落とす**。

`/youtubei/v1/live_chat/get_live_chat` のレスポンスを R2 と同じ MAIN world の `fetch` パッチで
処理し、**表示対象外の投稿者の `authorPhoto` を落としてからページに渡す**。
`authorPhoto` が無ければ `<img>` が生成されないので、ダウンロードもデコードも発生しない。

**アバターを表示する対象（ユーザー決定 2026-07-27）: モデレーターとチャンネルオーナーのみ。**
メンバー・認証済みチャンネル・一般視聴者は表示しない。

判定は `authorBadges[].liveChatAuthorBadgeRenderer.icon.iconType` を見て、`MODERATOR` または
`OWNER` を持つ投稿だけ `authorPhoto` を残す。メンバーバッジは `icon` ではなく `customThumbnail` を
使うため、`iconType` による判定で自然に除外される。

**受け入れ条件:**
- 一般視聴者・メンバー・認証済みチャンネルの投稿にアバターが表示されず、その画像リクエストも発生しない
- モデレーターとチャンネルオーナーの投稿にはアバターが表示される
- メンバーシップ専用スタンプ・絵文字・有料スタンプ・ギフト画像は表示される（アバターを落とす投稿でも）
- §6 の長時間ライブ視聴テストで、チャット表示ありの状態でもメモリ増加が受け入れ基準を満たす

**実装時に確認:** `OWNER` の `iconType` 値は実レスポンスで確認する（`MODERATOR` は確実だが、
オーナー表現がバッジ以外の形（`authorNameTextColor` 等）で来る可能性がある）。実装初手で
`get_live_chat` のレスポンスを 1 本ログに落として確定させる。

**保留（要件に含めない）:** チャット iframe の定期貼り直し。上記 2 つ（ノード上限・画像を作らせない）で
蓄積源は塞がる想定であり、**現時点で貼り直しが対処すべき対象が特定できていない**。§6 の実測で
それでも増加が続く場合にのみ、原因を特定したうえで検討する。

### R4. イコライザ

Web Audio API でページの `<video>` 要素にフィルタチェーンを挿す。

- 現行のバンド構成・プリセットを引き継ぐ（現行 `EqParams` の仕様に合わせる）
- 設定は永続化し、動画をまたいで維持する
- **ライブ配信でも効くこと**（現行の最大の不満点。§1 の表を参照）

**受け入れ条件:** VOD・アーカイブ・ライブ配信の 3 つで音が変化することを確認できる。
**注意:** `createMediaElementSource` は音声をグラフ経由に切り替えるため、拡張側の例外で
無音になり得る。フィルタ無効時は素通しになるフェイルセーフを持つこと。

### R5. チャット表示の調整

- 文字サイズの変更（現行: 10〜28px、既定 16px）
- パネル幅の変更（現行: 0.15〜0.6、既定 0.28）
- 設定を永続化する

現行はネイティブ描画だったが、拡張では CSS で実現する。**現行のクランプ範囲と既定値を引き継ぐ。**

### R6. コーデック / フレームレートの誘導（任意）

`MediaSource.isTypeSupported` と `HTMLVideoElement.prototype.canPlayType` を差し替えて、
特定コーデック（VP9 / AV1）や 60fps を避けられるようにする。

**この要件は優先度が低い。** 既存拡張（h264ify / enhanced-h264ify）が同じことを実証済みで、
併用すれば済む。自前で持つかは §6 の実測で「効果がある」と分かってから判断する。

### R7. SPA 遷移への追随（横断要件）

YouTube は SPA なので、動画遷移でドキュメントは再ロードされない。`document_start` は初回のみ発火する。

- グローバルのパッチ（R2 / R6）は JS コンテキストが維持されるため、初回に 1 回当てれば足りる
- **DOM を対象とする処理（R3 / R5）は遷移ごとに再適用が必要**。`yt-navigate-finish` 等を購読する

**受け入れ条件:** ホーム → 動画 → 別の動画 → ライブ配信、と連続遷移しても全要件が効き続ける。

## 6. 非機能要件（受け入れ基準）

**この節が方向転換の分水嶺だった唯一の空欄である。** 数値目標は実測後に確定させるが、
測定方法と比較対象は先に固定しておく。

### 測定条件

| 項目 | 内容 |
|---|---|
| 比較対象 | ①素の Chrome（拡張なし） ②拡張あり ③現行ネイティブアプリ |
| コンテンツ | 長時間ライブ配信 1 本 + VOD 1 本 |
| 時間 | 60 分連続再生 |
| 取得値 | プロセスツリー合算の Working Set / Private Bytes、CPU%、GPU%、累積ダウンロードバイト数 |
| サンプリング | 定期サンプリングし、**絶対値ではなく時間に対する傾き**を見る |
| チャット | 表示あり / なしの両方（チャットが最大の重量物である想定のため） |

### 満たすべき条件

1. **拡張ありは、素の Chrome より 60 分後のメモリ増加が明確に小さい**（最優先）
2. 拡張ありの累積ダウンロード量が素の Chrome より小さい
3. 拡張ありの定常 CPU が素の Chrome を上回らない

**③現行ネイティブアプリとの比較は、目標ではなく記録として取る。** ネイティブが軽いのは既知であり、
それを下回れないことは方向転換の時点で受け入れている（§8）。ただし**どれだけ離れているかは
記録に残す**。将来この判断を見直す人が同じ材料を持てるようにするため。

### 観測手段

MV3 の `webRequest` は観測用途では使えるため、遮断前後で何がどれだけ落ちたかを定量化できる。

## 7. 副次的に得られるもの（要件ではないが記録）

- **Windows 専用の制約が外れる。** 現行は DComp / D3D11 / PDH / WebView2 で Windows 固定。
- **ビルド環境の重さが消える。** libmpv（118MB）・VS Build Tools・`mpv.lib` の手生成・バンドル作成。
- **InnerTube の知識が死なない。** R2 はレスポンススキーマに依存するため、リゾルバ実装で
  蓄積した知識がそのまま活きる。腐食の対象が DOM セレクタからレスポンススキーマへ移る。

## 8. 受け入れるリスク・失うもの

| 項目 | 内容 |
|---|---|
| Blink / V8 / renderer の床 | 消せない。mpv 経路の軽さには届かない。**方向転換の時点で受け入れる** |
| GPU 負荷連動の自動デコード切替 | 等価物が無い。センサ（全プロセスの GPU 使用率）もアクチュエータ（HW/SW 切替）も拡張から届かない。**発火実績が無いため損失として計上しない**が、消えることは記録する |
| DOM を名指しする部分の腐食 | R3 / R5 は YouTube の UI 変更で壊れ得る。ただし**壊れても視聴は継続**し、症状は目視で分かる。標準 Web API にフックする R2 / R4 / R6 は腐食しにくい |
| ネイティブ実装の廃棄 | mpv 埋め込み・DComp オーバーレイ・InnerTube リゾルバ・resolver-sidecar・OAuth バックエンド・nsig。行数は大きいが、**追随コストが高い側が消える** |

## 9. 着手前に潰すべき未確定事項

1. **R2 の前提**: YouTube のネットワーク層が `fetch` / `XHR` を経由しているか（経由しないなら R2 は DOM 層に格下げ）
2. **R3 の効果**: アバター遮断とノード切り詰めだけで長時間の増加が止まるか。止まらないなら iframe 貼り直しが必須になる
3. **R4 の実現性**: `createMediaElementSource` が YouTube のプレーヤーと共存できるか（ストア上に同種の拡張が複数あるため成立見込みは高いが未自検証）
4. **§6 の数値**: 素の Chrome / 拡張 / ネイティブの 3 者比較。**これが黒（拡張が素の Chrome とほぼ変わらない）なら、この方向転換自体を見直す材料になる**
5. **R1 (b) の切り分け**: `heartbeat` / attestation を 1 本ずつ遮断して、何が壊れるかを個別に確定させる。
   （`playback`・`watchtime` は視聴履歴維持の決定により遮断対象外なので検証不要）
7. **広告トラッキング遮断の副作用**: 計測ビーコンを落としたときに、広告の再生自体が止まったり
   本編へ復帰しなくなったりしないか（プレーヤーがビーコンの応答を待つ実装になっている可能性）。
   壊れるなら該当分だけ (c) に戻す
6. ~~R3 のアバター判定範囲~~ → **決定済み（モデレーター + チャンネルオーナー）。** 残るのは
   `OWNER` の JSON 表現の確認だけで、実装初手のログ 1 本で片が付く（R3 参照）

上記 1〜4 は最小の PoC 拡張（R1 + R2 + R3 の骨だけ）で同時に潰せる。5 は PoC 中に同じ環境で確かめられる。
